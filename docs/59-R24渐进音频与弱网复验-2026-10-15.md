## 2. 后续候选已实现的路径修复

### 2.1 未缓存朗读边生成边播

实测供应商约 694ms 已返回首批 MP3 字节，而完整 144 字段落约 11.576s 才结束。旧路径等待完整段落、时间轴和缓存写入后才发播放地址，这是应用首音频尾部等待的一个确定原因。

候选保留原有 220 字规范分段及公共/家庭缓存键，不批量重生成已有音频，不增加 R2 副本。新客户端传 `streamAudio:true`；服务端收到第一批字节便发送签名的临时媒体地址。完整音频成功落盘后，再用 `segment-update` 更新同一队列对象的时间轴和后续重播地址，不重启正在播放的音频。旧客户端仍只收到完整段落。

临时注册表最多 32 个条目，每条最多 2MiB、120 秒、4 个读取者。各读取者按背压推进；失败、取消和过期会移除条目并结束读取。注册表满时回到完整段落播放，不跳过文本。此限制约束临时注册表，不等于整个进程的总内存上限。

媒体请求继续使用既有签名票据，校验家庭、会话和撤销状态；临时 URL 必须属于发起合成的同一会话。响应为私有、不缓存、不转换的 MP3 流。停止或切换播放会取消 SSE，并向供应商 HTTP 请求传递 AbortSignal；不能由此保证供应商即时停止计费。失败或取消的部分音频不作为完整缓存。

播放器还修复了跳段后丢弃后续 SSE、下一段尚未到达时提前结束、相同字符进度反复驱动 React 更新的问题。

### 2.2 资源发现及单书请求

服务端从当前构建的 Vite manifest 中选取对应孩子路由及其静态依赖，以 modulepreload 提前发现；不预取家长端和其他孩子场景。实测一轮冷弱网中，ChildHome/ReaderPage 请求开始时间从约 1538/2134ms 提前到约 280ms。这是资源发现证据，不是正文在 280ms 已可用。

HTML/manifest 和 CSP 内联脚本哈希是启动时快照，部署静态资源后须按现有发布流程重启服务。旧构建没有 manifest 时保留原加载路径。测试覆盖循环依赖、重复预加载、非法资源路径、HTTP 200、no-cache 和 CSP 引导脚本保留。

加载图及页头优先使用 9294B 的 WebP，旧浏览器保留原 PNG；favicon 改为 2086B 的 PNG。原始品牌素材保留，没有改变品牌图形。深链单书元数据与家庭验证并行请求，验证成功前不展示，失效孩子和旧身份的预取不能进入新档案；失败仍可重试。

### 2.3 阅读与书库交互

- 分页先读取高度，再按实际变化写列宽/间距/高度；ResizeObserver、图片及字体事件合并到一帧处理，保留首次同步测量和清理。
- 排版设置在正文首帧后准备。关闭时不启用焦点陷阱或正文隔离；仅保留无副作用的排版控件，录音等其他页签关闭时仍卸载。
- 路由更新使用 React Router 已提供的 transition 选项。浏览和全屏阅读使用独立的布局容器，避免同一个容器从有页头的窄布局突然移动到全屏。
