评审日期：2026-10-14。评审基线：`30592c1e01408c5c56d6ee896de305b307e705d6`。

**总体判定：桃阅读已经具备可供家庭使用的阅读工具基础，但尚未达到可放心扩大使用、支持低龄儿童独立使用的成熟产品标准。** 最需要解决的是“内容是否适合孩子、家长权限是否可信、读听续读是否一致、承诺是否经过验证”。书量和入口数量不能替代这些条件。

## 2. 从儿童阅读目标判断产品

孩子端的核心任务应是：**找到一本合适的书，容易开始，读或听不被打断，下次可靠接着读，并且可以安心停下来。** 家长端的核心任务应是：决定哪些内容可读，理解实际发生了什么，在需要时提供帮助，控制权限、费用与数据。

目前产品功能覆盖较广，但“适龄可信度”和“跨模式一致性”落后于功能数量。建议先把这两个核心任务做稳，再增加书目、AI 生成、拼读课程和成就入口。

| --- | --- | --- |
| 内容与适龄 | 不满足扩大使用门槛 | 277 本已上架书全部 pending，逐书导读为空；已确认不适合直接作为幼儿价值引导的文本被标为 3–5 岁 |
| 家长控制 | 不满足可信监护权限门槛 | 孩子所持家庭码可以直接取得家长角色；前端乘法题是防误入措施 |
| 基础阅读 | 有可保留的基础，设备可靠性仍需验收 | 正文、排版设置、目录、分页/滚动、版本进度与冲突处理已存在；真机未验收 |
| 听读与续读 | 多条路径各自可用，统一闭环不足 | 公共阅读、家庭阅读、独立听读的状态与降级不同；独立听读位置仅本机 |

## 3. 应保留的能力

以下不是重做对象，后续改进应保护这些能力：

- 公共书内容已有章、块、内容版本、来源和权利台账；发布接口要求人工批准声明，修改正文会使审校失效。问题集中在已上架存量与运营执行，不能误报成“完全没有发布门禁”。
- 公共书进度有串行提交、版本比较和冲突停止补写；有失败反馈、重试与离开页面 keepalive。不能把后文的极端丢进度风险表述成“完全不保存”。
- 阅读器提供主题、字号、字体、行距、分页/滚动；代表视口下正文与设置层可读，家庭书已复用部分阅读外观组件。
- 公共书离线采用主动保存、7 天有效和范围披露；本轮保存后断网重载可看到离线书架。离线试点没有隐瞒“进度不回传、无法及时同步下架”的边界。
- 家庭归属检查、家长 API 角色守卫、设备撤销、私有媒体会话票据、服务端密钥加密、安全头均有实现。家长角色的取得方式需要修正，但不是所有权限保护都不存在。
- 有家庭记录导出、在线家庭注销、恢复排除标记、一致性备份清单、SHA-256 校验与新路径恢复流程。应补演练和生命周期，而不是另造一套未经验证的备份系统。
- 对“找相同字”和文本再认已使用克制文案；独立听读也明确不计作理解或读完。不要再把这些活动扩张成未经验证的能力评分。

## 5. P1：优先处理及扩大使用前门槛

分类含义：“确认”指当前数据、源码或本轮复现支持；“源码风险”表示触发路径存在但尚未完成动态重现；“验证缺口”不是已经发生故障。P1 不表示每项都须停站，而表示不应在未处理或明确约束前扩大使用、作出相应承诺。

### R01｜存量上架书未进入当前审校闭环｜P1，确认

- **事实/触发**：生产 277 本书全部 `published/pending`，没有 `BookReviewEvent`，仅 2 本有非空 `reviewEvidence`。目录与可读判断只要求 published，因此存量内容会持续展示。
- **影响**：新发布接口有门禁，但现有书库不能据此被视为已经审核；缺少可追溯的“谁审过哪个版本”。
- **证据**：`production-readonly.json`；`apps/server/src/content/service.ts:238`、`:289`；`content/review.ts:11`；`content/seed.ts:65`。
- **处理/验收**：建立存量盘点和安全迁移，不直接批量把 pending 改为 reviewed。每本进入儿童书架的版本应有审读人、适龄/模式判断、来源证据和可追溯事件；尚未完成的书进入受控待审池。迁移先预览影响并保护原进度；所有目录、详情、正文、朗读入口及缓存应遵守同一发布规则。

### R02｜已确认古籍内容与幼儿推荐不匹配｜P1，生产数据与演示推荐确认

- **事实/触发**：《增广贤文》`zengguang-friends` 标为 3–5 岁，出现在该年龄档推荐。生产第 4 章正文与白话包含“养子不教如养驴，养女不教如养猪”；源码还包含从夫等性别等级表述，简介写“全本读来句句在理”。
- **影响**：幼儿会把未经解释的古代价值判断作为正向教育内容接收。问题不是禁止接触古籍，而是全本、年龄、引导方式与推荐语不匹配。
- **证据**：`production-readonly.json.contentSample`；首页截图；`content/packs/primer-zengguang.ts:14`、`:15`、`:68`、`:81`。
- **处理/验收**：先停止该版本面向幼儿的默认推荐，再人工选篇、审读白话和介绍，提供明确的历史语境与家长导读。对相近蒙学内容开展有记录的内容审查。不得仅改年龄标签就算完成，也不能从这一例推断全库全部不适龄。

### R03｜孩子家庭码能够取得家长权限｜P1，隔离复现确认

- **事实/触发**：只持有家庭码、请求 `role=parent`，加入接口返回 200 与 parent 令牌，家长设置接口 200；没有提供独立凭据或前端乘法答案。登录页是在取得令牌后才显示乘法门。
- **影响**：家庭码承担孩子加入与家长管理双重用途。角色 API 守卫存在，但不能抵御持码孩子或持码者选择家长身份。注销确认仍使用同一码，不能形成独立监护确认。
- **证据**：`audit-results.json.security`；`modules/family/service.ts:139`、`:361`；`pages/LoginPage.tsx:81`。
- **处理/验收**：孩子加入凭据只能签发孩子权限；家长使用独立认证或已验证家长设备批准，敏感动作在服务端再次确认。旧设备平滑迁移，不能锁死唯一家长入口。验收要求孩子码请求 parent 得不到家长令牌，直接调用管理/导出/删除接口被拒绝，已撤销会话不可复用。此测试未对生产家庭执行；本轮没有证实跨家庭数据泄漏。

### R04｜每日提醒没有覆盖持续读听旅程｜P1，源码确认

- **事实/触发**：`ritualWindow` 在首页挂载时请求，公共阅读器、家庭书与连续听读没有持续检查。服务端时长依据 Cosession；独立听读未创建对应会话，因此也不进入这一提醒统计。
- **影响**：家长设了每日阅读提醒后，孩子留在正文或听读页可能一直看不到提醒；“阅读和听读”承诺范围与实现不一致。
- **证据**：`pages/child/V8App.tsx:647`；`modules/ritual/routes.ts:78`；`pages/child/ListeningPage.tsx:46`。
- **处理/验收**：定义可解释的读/听使用口径，统一前台读听提醒，覆盖切书、后台恢复与跨日。采用温和提醒及可选择的收尾，不要求强制锁屏。隔离可控时钟下，孩子不回首页也能收到到点提示；独立听读的统计范围与家长设置文案一致，避免读听重复累计。

### R05｜家庭书音频故障将原始 JSON 展示给孩子，降级未兑现｜P1，隔离复现确认

- **事实/触发**：隔离环境禁用付费供应商，点击家庭书“朗读本章”，页面显示 `{"code":"TTS_UNAVAILABLE",...}`，其中提示“先用浏览器语音”，但没有出现可执行的浏览器语音降级。通用 SSE 客户端直接把非 2xx 正文作为错误文本。
- **影响**：朗读失败时孩子不知道下一步；“重新加载”不能修复服务端未配置问题。这里的 JSON 没有证明泄露密钥，但确实暴露了不适合孩子的实现信息。
- **证据**：[家庭书朗读错误截图](../output/playwright/product-review-20261014/demo-family-audio-unavailable.png)；`lib/api.ts:731`；`FamilyTrialPages.tsx:520`、`:533`。
- **处理/验收**：结构化解析错误，区分不可用、超时、离线、额度和浏览器拒播；给“继续看文字”“重试”及确实支持的备用语音操作。降级不可用时诚实说明。故障注入下不显示 JSON、不无限准备、不丢正文与当前位置；公共书/家庭书/连续听读保持一致。不能据本次故障注入断言生产日常朗读不可用。

### R06｜现有证据不足以保证“任何账户均不超过 10 GB”｜P1，确认的保护边界与验证缺口

- **事实/触发**：生产运维快照采于 10 月 13 日 14:05，已超过代码 15 分钟有效期。旧账户当时全桶和 multipart 为 6,216,605,670 bytes；新音频桶 3,322,051,743 bytes，明确 `wholeAccountVerified:false`。它们属于不同账户，不能以两桶相加代替各账户完整核查。
- **现有保护**：旧账户有本机跨进程锁、全账户枚举、9 GB 停写与失败预约保留；音频 `gatewayPut` 也有 5.4 GB 桶级保护，不能误报为没有容量守卫。但 Worker PUT 本身只限制单对象、校验哈希和条件新建；其他主机、手工写入、新桶及直接写 Worker 不共享本机累计预约。
- **影响**：现有正常路径有实质保护，仍不能证明所有账户和所有写入口都满足用户硬约束。过期快照不能当作当前低于上限，也不代表当前已经超限。
- **证据**：`runtime-readonly.json`；`lib/operations.ts:12`；`scripts/lib/r2-capacity.mjs:59`；`scripts/lib/r2-audio-gateway.mjs:67`；`workers/public-audio/src/r2-origin.mjs:33`。

### R27｜音频教学品质与精准对齐没有完成验证｜P2，已确认技术边界与验证缺口

- **事实/影响**：字级时间轴来自 MP3 时长加字符/标点权重估算，并非强制音素对齐；本轮没有完成全库多音字、古诗停顿、英文发音和译文音频抽检。高亮可以辅助跟读，但不支持声称精准识字教学或发音评测。
- **证据**：`modules/tts/timeline.ts:55`、`:92`；拼读入口仍标内测，录音回放不等于自动评分。
- **建议/验收**：先抽审并修正精选书架的关键音频，记录正文版本、声线、错误与修订。对齐达不到逐字精度时用段落高亮；保留手动读与录音回放，暂不扩大为完整教学课程。音频可播放、哈希一致和发音正确是不同验收层次。

## 7. 架构决策建议

当前规模下，**保留 React + Fastify 模块化单体、Prisma/SQLite 和现有部署方式，优先修正边界与可靠性**。仅有 1 个真实家庭、1 个孩子的数据，不足以证明数据库或单体已经成为瓶颈。现在直接引入微服务、重写前端或迁移数据库，会扩大迁移与运行成本。

建议按依赖顺序形成以下约束：

1. **内容契约**：一份已审读、绑定版本的内容状态，所有书架、推荐、正文、音频和离线入口遵守；人工批准不由机器检查替代。
2. **身份契约**：孩子凭据与监护管理分离；敏感动作以服务端认证为准，独立于 UI 是否显示。
3. **阅读契约**：书源适配、版本位置、读/听模式、保存状态与错误分类统一；沿用已有 CAS/冲突保护，逐步消除三套状态分叉。
4. **后台任务契约**：导入/生成持久化、可取消、幂等、有资源与金额预约；先在单体内实现受控任务，不把请求线程当无限任务队列。
5. **运行契约**：容量、恢复、依赖、性能的证据包含采样时间和覆盖范围；过期或覆盖不全必须显示未知，不能显示为健康。

只有实际并发、SQLite 写等待、API/解析竞争或运维可用性指标证明边界不足时，再决定是否增加工作进程、迁移数据库或把源站迁离个人 Windows 主机。每次迁移需有数据核对和回滚，而非为架构形式而迁移。
