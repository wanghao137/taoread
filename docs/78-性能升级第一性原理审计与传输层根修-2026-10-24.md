# 78 · 性能升级：第一性原理全轴审计与传输层根修（2026-10-24）

## 方法论

性能问题只有四个物理瓶颈：**传输字节、请求数/往返、解析/执行、渲染/布局**。
本轮对生产实例（read.taostudioai.com → cloudflared → 本机 8091）做全轴取证，
每一项先测量再定性，合格项明确记录（防后人重做），缺陷项修复并前后对比。

测量工具：curl 源站直连（头/编码/缓存）、Playwright 资源瀑布（登录→首页→书架→阅读器全流程）、
Node zlib 压缩基准、DNS/CF 头分析。**全部结论以源站 127.0.0.1:8091 实测为准**
（本机代理环境下公网 curl 会返回错误内容——同 URL 吐 442KB 假 CSS，docs/77 已记录该坑）。

## 修复 #1：品牌图 webp 化（commit 5480799）

登录页是每台设备的第一屏。6 处硬编码 `logo-256.png`（55KB）而 webp 版（9KB）闲置，
每次白付 45KB。新增 `BrandLogo` 组件（`<picture>` webp 优先 + png 回退——老 Safari<14
不支持 webp，兼容红线不变），替换 LoginPage/ParentHome/PrivacyPage/UtilityPage/
IconPeach（icons.tsx）全部入口。V8App/Loading 原本已是 picture。

## 修复 #2：源站启用 brotli q5（commit 5480799）

docs/35 B1 时代 `encodings: ['gzip','deflate']` 排除了 br——只声明 br 的客户端会拿到
**未压缩裸文件**（实测 229KB JS 裸传），且 gzip 非最优压缩。改为
`encodings: ['br','gzip','deflate'] + brotliOptions q5`。

Node zlib 基准确认了参数选择：**q5 = CSS 比 gzip 再小 30.3%、JS 小 5.2%、书架 JSON 小
12.2%，CPU ~14ms/次**；q11 虽再小 13.6% 但单次 680ms，家用 CPU 按需压缩不可接受。
家庭上行 ~95KB/s 是全站瓶颈，压缩率直接兑换用户时延。SSE（TTS）走 reply.raw 不受影响。

## 坑（本轮新增）

1. **HEAD 请求不触发压缩**——`curl -I` 看 Vary/编码会得出「缺 accept-encoding」的错误结论，
   必须用 GET 带响应体验证。
2. 本机代理环境公网 curl 的同 URL 假内容问题再次确认（性能验证一律走源站）。
3. TaskStop/按签名 taskkill 会误伤同签名进程（本轮把 8787 dev 实例连带杀过一次），
   本地多实例时按端口定位 LISTEN PID 再杀。
